# 给工业软件搭一个 Agent，我烧了差不多两亿 token

data-workbench 是我维护的一个数据分析软件，C++17 加 Qt 写界面层，内嵌 Python 跑 pandas 和 numpy，主要给科研实验数据做清洗、分析、绘图。最近这段时间我给它补上了 Agent 功能，一条对话面板嵌在主界面里，用户说「把这批数据按工况分组，画箱线图，标出离群点」，它就去查数据、算统计量、建图、调样式，画完的图落在软件的绘图区里，用户还能接着用鼠标手动微调。

整个过程里我手写的代码很少。真正干活的是 zcode、kimi code、qwen code、deepseek 这几个 agent harness，模型主力是 glm-5.2，中间穿插 qwen3.8-plus，前前后后烧了差不多两亿 token。

这篇文章讲三件事。我对 agent 的理解，data-workbench 这套东西的架构，以及怎么让 AI 替你把 agent 造出来。最后一部分是我最想讲的，因为它是方法论，你拿走就能用到自己的软件上。

## 一、先把 agent 祛魅

外面把 agent 讲得很玄，规划、反思、记忆、多智能体协作，名词一箩筐。你把任何一个真正能跑的 agent 拆开看，核心就是一个循环。

```python
while True:
    resp = llm(messages, tools=tool_schemas)
    if not resp.tool_calls:
        break   # 模型觉得没事可干了，输出最终回答
    for call in resp.tool_calls:
        result = execute(call.name, call.arguments)
        messages.append(result)
```

调模型，解析它想调什么工具，执行，把结果塞回消息列表，再调模型，直到它不再要求调工具。没了。所谓 agent 框架，langgraph 也好自己手写也好，都是在给这个循环加工程保障。

那工具是什么？工具就是两段东西。一段是 JSON Schema，告诉模型有这个东西可调、参数长什么样。另一段是执行器，模型说想调，你就真的去执行，把结果作为一条消息喂回去。模型从头到尾没碰到你的工具本体，它见到的只有 schema 和 description。再往下想，skill 是什么？一大坨 markdown，在合适的时机拼进上下文。系统提示词是什么？一段文本。子 agent 的定义是什么？还是一段文本。说到底，agent 开发的一半内容是模型调度，另一半就是提示词注入，把对的文本在对的时机拼进请求里。上下文工程这个词听着高级，干的事就是拼字符串，只是要拼得讲究。

想通这一层，agent 就没什么神秘感了，剩下的全是工程问题。

对工业软件来说，下面这个判断更重要。你的 agent 能干什么，完全取决于你暴露了多少工具。一个工具都不给，模型再聪明也只能陪你聊天。你把数据查询、绘图、文件读写、代码执行都包成工具递过去，它就能替用户干活。data-workbench 的 agent 能查数据、画图、调样式、写报告，靠的是 20 个工具，模型本身没有任何特殊之处。

这 20 个工具分布如下。

| 类别 | 数量 | 例子 |
|------|------|------|
| 数据查询 | 5 | list_data、get_data_info、query_data、get_column_stats、export_data |
| 绘图操作 | 10 | create_chart、add_curve、set_axis、add_annotation、save_chart_image |
| 文件与报告 | 3 | read_file、write_file、save_report |
| 代码执行 | 2 | run_code、run_script |

其中最值钱的是 run_code。它在一个持久命名空间里执行任意 Python，类 Jupyter kernel，变量跨调用保留，da_app、da_data 这些宿主对象预注入。前面 18 个工具是给模型铺的台阶，让它的高频操作走正门，别每次都现写代码。真到复杂需求，模型自己写脚本走 run_code，能力边界一下子宽出去几个数量级。代价是你得把代码执行的权限看紧，这个后面讲。

还有一个设计细节值得单独说。工具的 description 不是写给人看的注释，是写给模型看的使用手册。run_code 的描述有二十来行，讲清楚命名空间是持久的、返回的 result 是文本摘要不是 Python 对象、工程没保存时不要反复重试 run_script。这些话模型都会读，写得越明白它用得越对。很多人工具做了不少，agent 就是不好用，问题往往出在描述偷懒。

## 二、data-workbench 这套东西的架构

### 进程模型

data-workbench 是桌面软件，C++ 生态里没有趁手的 agent 框架，langgraph 在 Python 那边。所以架构拆成两半。推理循环、上下文管理、重试、子 agent 编排，全部跑在一个 Python 子进程里。工具执行全部留在 C++ 主进程。两边用 stdin/stdout 管道通信，一行一条 JSON。

```
┌─────────────── C++ 主进程 (Qt) ───────────────┐
│  界面 / 数据工作区 / 绘图区 / 工具执行         │
│  DAAgentBridge (QProcess + JSON Lines 协议)   │
└──────────┬───────────────────▲────────────────┘
      stdin │ user_msg          │ token / tool_call / message_end
      写    │ tool_result       │ stdout 读
           ▼                   │
┌─────────── Python 子进程 ──────────────────────┐
│  langgraph 推理循环 / 上下文压缩 / 重试        │
│  langchain-openai → OpenAI 兼容 API (流式)    │
└────────────────────────────────────────────────┘
```

工具执行留在 C++ 是有意为之。agent 要操作的数据在工作区内存里，DataFrame 的引用、图表容器、绘图窗口，全在主进程。工具留在 C++，天然摸得到这些对象，不需要文件中转。LLM 那边只拿到工具 schema，真正执行时经管道 RPC 回调到主进程，查到什么、画了什么，直接就是界面上的真实对象。这是工业软件做 agent 最舒服的一点，你的工具层就是你的业务层，中间不需要任何胶水。

推理放子进程则是为了隔离。LLM 一思考就是几十秒，这活要是塞进主线程，界面直接冻住。Python 子进程崩了，主程序还活着，桥接层检测到异常退出会自动重启它，从磁盘上的会话记录恢复历史，重发最后一条用户消息，用户最多感觉到卡了一下。重启上限三次，连续崩就老实报错。

协议本身很简单。C++ 往 stdin 写 user_msg、tool_result、load_session、reconfigure 这些，Python 往 stdout 写 token、tool_call、message_end、usage、error。stdout 只许走协议，日志全部走 stderr，混进去一行整个解析就乱了。

### 一条 token 的旅程

流式输出的完整链路值得单独讲，因为这里每个环节都有坑。

Python 里 llm.astream() 逐 chunk 拿到增量文本，每个 chunk 发一行 JSON 到 stdout。C++ 桥接层按行解析，转成 Qt 信号，一路传到聊天面板。面板用 QWebEngine 加 QWebChannel 渲染，chat.js 收到 token 后追加到气泡的原文缓冲上，每 50 毫秒才做一次 markdown 重渲染。不防抖的话每个 token 都触发整条消息的全量重解析，消息一长就是平方级的卡顿。

两个容易栽的细节。其一，流式 chunk 里的 tool_calls 是按 index 分片的增量，必须把所有 chunk 累加完才能读出完整参数，逐 chunk 当完整参数用，拿到的是残缺 JSON。其二，token 用量有两条通道。流式开始前先用 tiktoken 估算一版发出去，让 UI 的进度条先动起来，流结束后用最后一 chunk 里携带的 usage_metadata 覆盖成权威值。估算值只用来驱动进度条，不记账，真实账目以 API 返回为准。

### 权限，工业软件绕不开的一课

run_code 等于给了模型一条任意代码执行的通道，write_file 让它能写你的磁盘。权限系统在这种情况下就不是可选项。

data-workbench 的权限引擎做了两个维度。模式维度三档，全自动、自动、每步必问。工具维度五级，只读、应用内变更、文件写入、代码执行、未知。决策顺序是硬拒绝优先，系统目录的 deny 规则在任何模式下都生效，全自动模式也拦，删都删不掉。然后全自动直接放行，自动模式按分级走规则，比如写文件先看目标路径匹不匹配 `${workspace}/**` 这类 glob 规则。文件写入还有会话记忆，用户批准过一次写某个目录，同一会话内往这个目录写就不再问了。

有个设计我挺得意。审批卡等待期间，所有超时计时全部暂停。用户可能去倒水了，可能下班了，回来点批准，工具从头执行，超时从执行那一刻重新算。你要是不做这个区分，用户回来会发现任务早就超时死掉了，批准了个寂寞。

还有一处反直觉的。拒绝代码执行时，回给模型的文案是固定的脱敏话术，不告诉它命中了哪条规则。你把规则细节喂给模型，它下一轮就学会换个写法绕过去。模型很聪明，别教坏它。

默认模式设成了全自动。这是桌面软件，用户操作的是自己机器上自己的数据，弹窗问个没完体验极差。硬拒绝那条底线兜住系统目录，其余的信任用户。要是多人共用的环境，切到自动模式就行。

### 子 agent

主 agent 干探索类的活容易把上下文塞爆。比如让它把工作区十几个数据集挨个摸一遍，每个都要看 schema、算统计量，几轮下来窗口就满了。这种活适合派子 agent。

data-workbench 里子 agent 的定义就是一个 markdown 文件，frontmatter 写 name、description、工具白名单，正文写系统提示词。内置了一个 explore，只读探索用的，白名单里只有数据查询和读文件。主 agent 手里有一个 dispatch_subagents 工具，它的描述里自动拼着当前所有可用子 agent 的清单，主 agent 看着清单按需派发。派发时给它完全自包含的任务描述，子 agent 看不到主对话的上下文。

编排器在 Python 侧，做了并发限流、墙钟超时、停止级联。几个数字，并发最多 2，一批最多 4 个任务，单个任务 600 秒上限。长任务期间每 30 秒发一次心跳，不然主进程的看门狗会把没有 token 输出的派发误判成卡死。

权限上，子 agent 和主 agent 走同一道门。executeTool 前置执法，白名单只是收窄它能用什么工具，该问用户的照样问，审批卡上会标注这个调用来自哪个子 agent。子 agent 的工具调用不写进会话记录也不渲染到聊天流，只执行，不然十条并行探索把界面刷成瀑布。

这里有个我称之为「身后执行」的坑。子 agent 发起一个需要审批的调用，用户还没点，任务先超时死了，用户过了十分钟随手点了批准，这个调用真的会执行，但结果已经没有人消费，副作用却落在用户的软件里。所以编排器盯着任务终态，任务一死立刻把对应的审批卡撤掉。

### 领域 agent 就是一个 md 文件

平台层之外，data-workbench 有个提示词库。每个 agent 是 daAgent 目录下的一个 md 文件，界面上点一下执行，全文作为一条用户消息发出去，模型按里面写好的流程干活。我写了一个多联机故障诊断的 agent，几十行 markdown，把诊断维度、要调什么工具、按什么顺序调、输出什么结构写清楚，它就能对工作区里的机组运行数据做一套完整的诊断分析，产出一份结构化报告。

插件也能经 registerBuiltinAgent 注入自己的领域 agent，用户编辑过就不覆盖。

对工业软件来说这条路子特别划算。你的领域知识、老师傅的经验、固定的分析流程，全都不用写代码，写成 markdown 就变成了一个可复用的自动化入口。卖软件的时候这就是产品化定制的能力，实施人员改 md 文件，不用等开发排期。

## 三、踩过的坑

这部分是两亿 token 里最贵的部分，捡几个有代表性的说。

**静默崩溃 62097。** langchain 冷启动要十几秒，这是 import 本身的开销，机器慢的话更久。我的 ready 超时是 60 秒，正常机器上绰绰有余。问题是 C++ 这边等不到 ready 就 TerminateProcess 强杀，而 Python 的 stderr 是块缓冲，被强杀时缓冲没刷出来，日志里什么都不留。表现出来就是子进程凭空消失，exitCode 是个莫名其妙的 62097，没有任何报错信息。修法有两层，booting 心跳必须在 import langchain 之前就发出去，让 C++ 知道进程还活着别急着杀，同时把 stderr 改成行缓冲。这类 bug 最气人的地方在于它只在慢机器上出现，你自己的开发机上永远复现不了。

**Windows 的 asyncio。** QProcess 的管道在 ProactorEventLoop 上直接报 WinError 6，SelectorEventLoop 又不支持管道 transport，两头堵。最后的做法是 stdin 用一个后台线程阻塞读，读到数据再 call_soon_threadsafe 投递回事件循环。这种问题 Python 官方文档不会告诉你，只有撞上才知道。

**悬空的 tool_call。** 历史消息里只要有一条 assistant 消息带着 tool_calls 而后面没有配对的 tool 结果，OpenAI 兼容 API 直接拒绝整个请求，对话永远恢复不起来。进程只要在工具执行途中崩过一次，磁盘上就会留下这种残缺记录。所以加载会话时要扫一遍历史，给每个没配对的 tool_call 塞一条占位的 tool 结果，告诉模型这次调用被打断了、结果不可用。tool.call 必须有配对的 tool.result，这条不变式值得刻在脑子里，很多莫名其妙的对话卡死都是它引起的。

**上下文压缩。** 这块借鉴了 qwen-code 和 kimi-code 的思路，做了四道防线。工具结果超长先截断成预览加占位提示，让模型知道可以换参数重取。估算 token 超过窗口的 85% 触发自动压缩，压缩方式是保留开头一两轮和最近十来条原文，中间部分让模型自己写一份交接笔记，用第一人称，写清用户最初想要什么、已经做完了什么、还有什么不知道。连续三次压缩失败就熔断。最后一道是反应式兜底，API 真报了 context 超限错误，捕获它，强制压缩，重试一次，打断「报 400、局部处理、再报 400」的死循环。

**循环空转。** agent 有时会反复调用同一个工具，同样的参数，一遍一遍，安安静静把 token 烧光。防了两层，连续相同签名的调用先返回引导性的结果劝它换个思路，连续三次完全相同就强制剥离 tool_calls 结束本轮。

## 四、怎么让 AI 替你把 agent 造出来

前面讲的都是结果。这一节讲过程。

整个 agent 功能我没有手写多少代码，干活的是 zcode、kimi code、qwen code、deepseek 这几个 harness，模型主力 glm-5.2，穿插 qwen3.8-plus。两亿 token 听着吓人，折成 API 账单，比一个工程师一个月的工资低得多，产出的是一整套带权限、带子 agent、带会话管理的生产级功能。

我的体会是，干这件事一个 agent 就够了。你不需要给「造 agent」这个活本身再组一个 multi-agent 开发团队，那种编排带来的协调成本远大于收益。你需要做的是把方向感建立起来，然后一段一段把提示词喂过去，让它一步步长出来。

### 先有一张能力地图

一个完整的 agent 由哪些能力组成？你不必一次全做，但得知道每一项的存在和它解决的问题，不然你不知道自己缺什么。

| 能力 | 解决什么问题 | 必要性 |
|------|------------|--------|
| 推理循环 | 调 LLM、解析 tool_calls、执行、回传、继续 | 必要 |
| 工具系统 | 声明式工具 + JSON Schema + 注册执行 | 必要 |
| 流式输出 | 逐 token 推到 UI，边生成边看 | 必要 |
| 通信与隔离 | 推理不阻塞主程序，双向流式协议 | 必要 |
| 对话 UI | markdown 渲染、工具调用折叠、双向桥接 | 必要 |
| 人机交互 HITL | agent 能在对话流里向用户提问，回答后继续 | 必要 |
| 系统提示词 | 分段拼接、运行时注入、防注入转义 | 必要 |
| 配置与安全 | LLM 配置、连接测试、凭据加密 | 必要 |
| 上下文管理 | token 估算、阈值压缩、摘要重组历史 | 必要 |
| 循环防卡死 | 最大步数、循环检测、配对兜底 | 必要 |
| 重试与恢复 | 429、断网、限流下退避重试 | 必要 |
| 会话管理 | 多会话、持久化、崩溃后恢复 | 按需 |
| 权限系统 | 每工具允许/询问/拒绝、路径保护 | 按需 |
| 子 agent 调度 | 派发独立子任务、收窄工具与权限 | 按需 |

前三项做完，一个能跑的 demo 就有了。往后每一项都是在堵一种具体的死法，长对话爆窗口、空转烧钱、断网卡死、崩溃丢会话、误删用户文件。地图上从左往右、从必要到按需，就是你的开发顺序。

### 第一段提示词，逼它先出计划

agent 是个大工程，直接让 AI 上手写代码必翻车。第一段提示词的任务是让它先出计划，而且是架构中立的计划，先看清楚你的项目再动手。

这段提示词的结构长这样，可以直接抄走改。

> 为 {平台名} 新增 AI Agent 能力，让用户在 {使用场景} 通过自然语言对话，调用大模型对 {数据} 进行 {分析、可视化、报告生成等能力}。
>
> 第一步，识别我当前系统的技术架构和现有能力。桌面端还是 Web 端、什么框架、什么构建系统、现有的数据与可视化能力如何，据此选择与之匹配的隔离方式、通信方式、渲染方式。下面每条都是平台中立的设计要求，只说目标与原因，具体机制由你按我当前架构选，在计划里说明理由，与我的架构冲突先和我确认。
>
> 一、推理与宿主隔离。LLM 推理、API 调用、工具编排放在不阻塞主程序的执行单元里，桌面端就是子进程或独立线程。不使用时零开销，执行单元出问题主程序要能恢复到可用状态。
>
> 二、框架与 LLM 接入。选一个原生支持「向用户提问、用户选择后继续推理」的 agent 框架，Python 后端 LangGraph 是成熟候选，其它栈给出两三个候选和取舍。LLM 走 OpenAI 兼容 API 加流式，做 provider 抽象，不绑死任何一家 SDK。
>
> 三、流式输出。逐 token 到 UI，chunk 里的 tool_call 按 index 累积拼接，不能逐 chunk 当完整参数。渲染增量追加加防抖，工具调用和结果在对话流里折叠展示。
>
> 四、人机交互。提问直接出现在对话流里，不弹模态窗，用户选择后答案回传继续推理，支持多轮提问。
>
> 五、工具体系。统一接口，getToolSpec 返回 JSON Schema，execute 返回 JSON 结果。大数据集返回摘要而非全量，失败返回 success false 不抛异常，带超时。
>
> 六、系统提示词分段拼装，平台基础加领域扩展加工具规格自动注入，外部注入的内容转义后再拼，防 prompt 注入。
>
> 七、分层架构。通用能力做平台模块，领域能力经注册注入，不把领域逻辑写进通用模块。
>
> 八、精确规则用脚本，LLM 负责推理和表达。阈值判断、窗口检测这类精确活不交给模型，它不可靠。固定脚本输出结构化结论，agent 拿结论去验证、可视化、解释。
>
> 九、配置与安全。api key 加密存储，不写日志不打控制台。文件工具限制在工作目录，路径词法规范化防越界，拒绝敏感文件。
>
> 十、错误处理。每个 tool.call 必须有配对的 tool.result，中断、超时、取消都要合成错误结果兜底，否则下一轮请求会被 provider 拒绝，对话卡死。
>
> 十一、分阶段交付，每阶段可独立验证。先模块骨架，再核心循环，再对话 UI，再生命周期，再内置工具，再设置页。每阶段实现前先给我看设计，确认后再做。

计划阶段别省。我在这个阶段还让 agent 给项目写了一份 AGENTS.md，把模块边界、编码规范、已有约定全部写进去，后面每一轮开发它开工前都会先读这份文件，返工量肉眼可见地降下来。data-workbench 是五层架构，agent 框架库放在接口层，不依赖任何 GUI 模块，UI 在界面层，两边靠应用层的信号接线拼起来。这种边界要是靠口头反复叮嘱，两亿 token 都不够交学费，写进文件一次就管到底。

### 每补一块能力，一段提示词

计划批准后按阶段推进。每一段提示词的套路都一样，先让 AI 识别你现在的代码结构和数据流，再给设计要求，最后带验收标准。几个关键能力的要点。

**上下文管理。** token 估算用启发式就够，ASCII 按 4 字符每 token，中文按 1 到 1.5 字符，真实 usage 回来就覆盖估算值，估算只用来触发判断不记账。压缩阈值分级，85% 自动压，贴着上限强制救援，给摘要这次额外的 LLM 调用留 buffer。压完的历史是「摘要 + 最近若干轮原文 + 省略标记」，不要一刀切全摘要，原文比摘要可信。连续失败要熔断。构造一个超长对话验收，确认压缩后能继续、不丢关键事实、不报超限。

**循环防卡死。** 最大步数上限，超限直接停。连续相同的 tool_call 判卡死，停止并提示。验收就构造一个让 agent 反复调同一工具的场景，确认它会被停下来。

**重试与恢复。** 指数退避加抖动，尊重服务器的 Retry-After 头，只重试 429 和 5xx，参数类错误不重试。每次重试发事件给 UI 让用户看得见。agent 提问等用户回答期间，看门狗必须暂停，用户不在电脑前是正常行为，这一条很多实现都栽过。流式中断要能恢复，上下文超限要联动强制压缩后重试。

**会话管理。** append-only JSONL，每行一条记录，容忍末行截断。恢复时用和 live 执行完全相同的路径回放，不调模型不执行工具不发 UI 事件。uuid 加 parentUuid 做链，断链能检测能降级。验收就是中途 kill 进程再恢复，历史、工具结果、token 用量都能还原且对话能继续。

**权限。** per-tool 规则，deny 优先于 ask 优先于 allow，路径匹配用 gitignore 风格的 glob，词法规范化防前缀碰撞绕过。yolo、auto、manual 三档模式。验收场景是读 .env、访问工作区外路径、执行危险命令，确认被拦或被问。

**子 agent。** 独立实例不共享状态，用 profile 收窄工具和权限，禁止子 agent 再派同类子 agent 防扇出爆炸。这里有个顺序上的忠告，先把权限做完再上子 agent。子 agent 是会自主发起工具调用的实体，没有权限门看着它，它做出什么让步性操作你都得认，等发现再回头补权限，要改动的面会大到你怀疑人生。我就是先做权限再做子 agent 的顺序，后来复盘觉得这是整个开发里最正确的决定之一。

### 你的角色是什么

整个过程里，你的工作从写代码变成了三件事。

审计划。每个阶段的方案在它动手前过一遍，方向歪了当场掰，代码写完了再掰成本翻十倍。

盯验收。上下文、重试、权限、会话这几个模块出的错都相当隐蔽，超时竞态、静默崩溃、悬空调用，验收时要较真，把异常场景真的构造出来跑一遍。

沉淀铁律。每次踩坑，把原因和修法写进 AGENTS.md。data-workbench 的 agent 模块现在攒了 17 条铁律，每一条背后都是一次真实事故，booting 心跳必须先于重依赖导入、token 流必须累加后才能读 tool_calls、提问只发一次。这些东西 agent 每轮开发都会读，等于给整个开发过程装了防倒退的护栏。两亿 token 买回来的东西，一大半其实沉淀在这些文件里。
